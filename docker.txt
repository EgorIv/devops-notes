Образ - шаблон, из которого делают контейнеры. В нем есть файловая система, 
компоненты, настройки запуска приложения. Контейнер - созданный из образа экземпляр 
с собственным состоянием выполнения: процессами, настройками.

docker build -t api:v1 . 
build - собрать образ по инструкциям Dockerfile 
-t - назначить образу имя и тег 
api:v1 - имя образа api, тег v1 
. контекст сборки - текущая директория

docker run -d --name task-api -p 8000:8000 task-api:v1 
run - создать контейнер и запустить его 
-d - запустить в фоне 
--name task-api - назначить имя 
-p 8000:8000 - назначение портов: порт хоста и порт контейнера 
task-api:v1 образ, из которого создается контейнер

docker ps -a - показывает контейнеры -а показывает в том числе остановленные

docker images - показывает образы

docker stop ... - останавливает рабочий контейнер

docker start ... - запускает остановленный контейнер

docker rm ... - удаляет контейнер






Dockerfile - текстовый файл с инструкциями, по которым докер собирает образ. не 
скрипт, часть инструкций выполняется при сборке, а команда запуска приложения 
задается отдельно.

Пример:
FROM python:3.13-slim  - инструкция, задающая базовый образ, на основе которого собирается новый

WORKDIR /app  - рабочая директория внутри образа и контейнера, где /app абсолютный путь внутри контейнера

COPY app.py .  - инструкция копирования файлов из контекста сборки в образ, app.py источник в контексте сборки, а . место назначение относительно текущей директории /app

EXPOSE 8000  - указывает, что приложение в контейнере предполагается (не ставится по умолчанию, скорее для других людей помечается) доступным на порту 8000. внутренний порт, но не обязательно будет на этом порту, если при создании контейнера укажут другой порт

CMD ["python", "-u", "app.py"] - задает команду по умолчанию, которую Docker выполняет при запуске контейнера. 
"python" - запускаемый интерпретатор
"-u" запуск с небуферизированным стандартным выводом, чтоб вывод программы появлялся в логах, а не оставался внутри контейнера
"app" - файл, который нужно выполнить

Различия между CMD и RUN:
RUN - выполняет команду во время сборки образа
CMD - задает команду при запуске контейнера

ADD - копирование с дополнительными возможностями: может автоматически распаковывать поддерживаемые локальные архивы, некоторые возможности работы с URL и Git 0источниками
Пример:
ADD archive.tar.gz /app/ - при добавлении локального tar-архива можнт распаковать его в каталог назначния
Лучше использовать COPY, его поведение понятнее и предсказуемее. Использовать ADD лучше, когда нужна его доп функциональность.

ARG - позволяет передавать значения в Dockerfile при сборке образа.
Сам по себе не создает перемнную окружения для работающего приложения.
Значения аргументов могут быть видны в метаданных сборки или истории, поэтому нельзя использовать для передачи секретов.
 Например:
ARG PYTHON_VERSION=3.13
FROM python:${PYTHON_VERSION}-slim
Но при сборке можно указать другое значение:
docker build --build-arg PYTHON_VERSION=3.13 -t task-api:v1 .
--build-arg - передать значение аргумента сборки

ENV - задает переменные окружения, которые сохраняются в конфигурации образа и доступны контейнеру во время выполнения. Например:
ENV APP_PORT=8000
ENV APP_ENV=production

USER - пользователь внутри контейнера. 
По умолчанию многие контейнеры запускают основной процесс от root, но для приложения безопаснее по возможности использовать отдельного непривилегированного пользователя

ENTRYPOINT - основной исполняемый процесс, его используют, когда образ предназначен для запуска определенного приложения или утилиты.
Различия медлу ENTRYPOINT и CMD:
ENTRYPOINT - что именно запускаем
CMD - аргументы по умолчанию
Пример:
ENTRYPOINT ["python", "-u"]
CMD ["app.py"]
по умолчанию эквивалентно python -u app.py, но если выполнять другой файл, например other.py, то окружение останется такое же, а CMD заменится.






.dockerignore - что не отправлять в контекст сборки, не похож на .gitignore, так как первый управляет контекстом сборки, а второй - тем, какие файлы git игнорирует при отслеживании
Пример:
.git/
.venv/
__pycache__/
*.pyc
.env

.git/ — не включать Git-метаданные;
.venv/ — не включать локальное виртуальное окружение Python;
__pycache__/ и *.pyc — исключить кэш и скомпилированные файлы Python;
.env — не передавать файл с переменными окружения в контекст сборки





Сети Docker (docker networking)
сеть докер обеспечивает взаимодействие между контейнерами и, при необходимости, между контейнерами и хостовой машиной.
каждый контейнер имеет собственное сетевой окружение.

Основные встроенные сети:
bridge - стандартная сеть докер. контейнеры подключаются к ней для сетевого взаимодействия
host - контейнер использует сетевое окружение хостовой машины вместо отдельной сетевой изоляции обычного типа
none - обычное сетевое подключение контейнера отключено

для приложений с несколькими контейнерами часто создают собственную bridge-сеть. она позволяет контейнерам обращаться друг к другу по именам, это удобнее, чем напрямую использовать ip адреса, тк они могут меняться при пересоздании контейнеров.

В пользовательской сети Docker предоставляет DNS-разрешение имен контейнеров.
Например, если контейнер базы данных называется postgres, приложение может подключаться к бд по адресу (имени и порту):
postgres:5432 

localhost внутри контейнера указывает на этот же контейнер, а не на другой контейнер и не на хостовую машину

публикация порта контейнера происходит параметром -p при создании контейнера форматом:
-p порт_хоста:порт_контейнера
-p 8001:8000 - означает, что порт 8001 на хосте перенаправляет соединения на порт 8000 внутри контейнера.

Публикация порта (не обязательная) позволяет обращаться к приложению через хостовую машину 

Основные команды:
docker network ls - показать список сетей
docker network create ... - создать сеть с нужным именем
docker network inspect ... - посмотреть настройки сети и подключенные контейнеры
docker network connect _network-name_ _container_ - подключить контейнер к сети
docker network disconnect _network-name_ _container_ - отключить контейнер от сети
docker network rm _network-name_ - удалить сеть, если к ней больше не подключены контейнеры





Docker тома (volumes)
Контейнер содержит собственный изменяемый слой файловой системы. Данные записанные только в этот слой, теряются при удалении контейнера.
Том - область хранения данных, управляемая докером и подключаемая к контейнеру.

например, postgresql хранит файлы бд в /var/lib/postgresql/data, если подключить к данному каталогу том, данные базы смогут сохраняться после удаления и пересоздания контейнера

Том существует отдельно от контейнера, контейнер использует для чтения и записи данных том, новый контейнер может подключить тот же том и получит доступ к данным.
Тома бывают именованные и анонимные, анонимные создаются без явно заданного имени, докер ему присваивает сгенерированный id.

Основные команды:
docker volume ls - показать список томов
docker volume create ... - создать том
docker volume inspect ... - показать информацию о томе
docker volume rm ... - удалить том, если он не используется контейнером 
docker volume prune - удалить неиспользуемые тома в соответствии с правилами команды.

для подключения тома используют параметр -v или более развернутый --mount:
-v postgres-data:/var/lib/postgresql/data
